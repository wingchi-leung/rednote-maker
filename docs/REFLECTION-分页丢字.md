# 分页丢字问题技术分析

## 问题描述

文字转图片时，某些段落没有出现在下一页，也没有出现在当前页——在界面上看起来就是「这一大段文字不在下一页，直接没了」。

## 根本原因

**卡片使用固定高度 + `overflow: hidden`，当分页估算不准确时，超出部分被静默裁切。**

预览区域和导出用的卡片都是固定尺寸（900×1200px），内容区使用了 `overflow: hidden`，超出部分会被裁掉。

---

## 历史实现演进

### 第一版：字数估算（已废弃）

**问题**：使用 `maxCharsPerPage = 650` 字符数上限来切页。

同样 650 字在不同排版下占用高度差异巨大：
- 纯段落、长句、少换行 → 行数少，可能勉强能放下
- 列表多、标题多、短句多、换行多 → 行数多，实际渲染高度远超一屏，底部被裁掉

**为何反复出现**：字数与高度不是线性关系，字体、行高、主题、列表/标题样式都会改变「每字占用的垂直空间」。

### 第二版：固定高度估算（有 bug）

**改进**：改为基于「高度估算」的分页，计算每个块（标题、段落、列表）的像素高度。

**遗留问题**：使用固定的 `padding: 32px` 和 `lineHeight: 28px`，完全忽略了用户选择的：
- **密度设置**：紧凑(24px, 1.5) / 舒适(32px, 1.75) / 宽松(40px, 2.0)
- **字号设置**：小(14px) / 中(16px) / 大(18px)

当用户切换密度或字号时，实际渲染高度发生大幅变化，但分页算法毫不知情，导致估算与实际严重不符。

---

## 当前实现（第三版）

### 核心思想

**根据用户实际选择的渲染参数，精确计算每页可容纳的内容高度。**

### 关键改进

1. **接收渲染参数**
   ```typescript
   calculatePages(markdown, { density, fontSize })
   ```

2. **根据密度计算实际 padding**
   - 紧凑: 24px
   - 舒适: 32px
   - 宽松: 40px

3. **根据字号和密度计算实际行高**
   ```
   lineHeight = fontSize × density.lineHeightRatio
   例如：中号(16px) × 舒适(1.75) = 28px
   ```

4. **精确估算每个块的渲染高度**
   - 标题：考虑标题字号倍数（h1=2x, h2=1.75x, h3=1.5x）、换行、边距
   - 段落：根据内容宽度估算换行数
   - 列表：考虑左边距和项目符号
   - 代码块：使用等宽字体行高

5. **高度累加分页**
   ```
   可用高度 = 卡片高度(1200) - padding × 2
   安全高度 = 可用高度 × 85%  // 留 15% 安全边距
   ```

6. **智能拆分超大块**
   - 优先在换行符处分割
   - 其次在标点符号处分割
   - 最后在空格处分割

## 已知限制

1. **仍然是估算，非实际测量**
   - 算法基于数学模型估算高度，而非渲染后测量 DOM
   - 极端情况下（如嵌套引用、复杂表格）可能有偏差

2. **主题样式差异**
   - 某些主题有特殊装饰（如 Apple Notes 布局的头部）
   - 当前算法尚未考虑这些额外空间占用

3. **85% 安全边距**
   - 保守策略确保不丢字，但可能导致每页内容偏少
   - 可在未来根据实际渲染测量动态调整

---

## 未来优化方向

1. **实际渲染测量**
   - 在隐藏的 DOM 中渲染内容，测量真实高度后分页
   - 或使用 `element.getBoundingClientRect()` 动态校验

2. **主题感知**
   - 为不同模板（classic/dark/parchment/morandi）配置不同的空间占用
   - 考虑特殊布局（如 Apple Notes 头部）的高度

3. **动态安全边距**
   - 根据用户反馈和实际测量结果，动态调整安全边距比例
   - 平衡「不丢字」和「内容利用率」
